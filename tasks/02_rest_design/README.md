## 1. Сценарий и границы

* **Выбранный вариант:** Прогнозирование спроса для розничной сети.
* **Кто использует прогноз и какое решение принимает по результату:**  
  Прогноз используют категорийные менеджеры торговой сети (через веб-кабинет) и автоматизированная ERP/WMS-система управления запасами. На основе прогноза менеджер утверждает объем закупки партий товаров у поставщиков, а WMS-система планирует распределение остатков по складам и график поставок в торговые точки, предотвращая дефицит (out-of-stock) и затоваривание полок.
* **Какие данные нужны для получения прогноза:**  
  Идентификатор номенклатурной позиции (`product_id`), идентификатор магазина (`store_id`), целевой календарный месяц планирования (`period` в формате `YYYY-MM`), а также опциональный параметр планируемой скидки (`discount_percent`).
* **Что входит в ваш сервис, а что относится к внешним системам:**  
  * **Входит в проектируемый сервис:** эндпоинты приема запросов на расчет прогноза, валидация входных данных, сохранение истории сформированных прогнозов, выдача сохраненных отчетов по фильтрам и вызов внутреннего модуля ML-инференса.
  * **Относится к внешним системам:** кассовые узлы (POS-терминалы), базы данных сырых чеков, сервисы прогноза погоды и учетная система 1C/ERP. История продаж и чеки принадлежат внешним системам — наш сервис забирает из них агрегированные признаки, но **не предоставляет собственных эндпоинтов** для работы с кассовыми транзакциями.

## 2. Ресурсы и операции

*Перенесите нужные связи из контекстной схемы ПР № 1. Укажите 3–4 операции только для проектируемого API.*

| № | Потребитель / связь ПР № 1 | Ресурс | Метод и путь | Назначение / вход |
| :-: | :--- | :--- | :--- | :--- |
| 1 | Веб-кабинет менеджера / Связь 3 | Прогноз | `POST /forecasts` | Создание и расчет нового прогноза спроса. Вход: JSON-тело с параметрами (`product_id`, `store_id`, `period`, `discount_percent`). |
| 2 | Веб-кабинет менеджера / Связь 3 | Прогноз | `GET /forecasts/{forecast_id}` | Получение сохраненного результата прогноза по его уникальному идентификатору. Вход: path-параметр `forecast_id`. |

## 3. Примеры данных

### Операция 1: POST /forecasts (Создание прогноза)
* **Обязательные поля и их смысл:**
  * `product_id` (integer) — идентификатор товара в торговой номенклатуре. Обязательное поле.
  * `store_id` (integer) — идентификатор торговой точки (магазина). Обязательное поле.
  * `period` (string) — планируемый период в формате `YYYY-MM`. Обязательное поле.
  * `discount_percent` (integer) — планируемый процент промо-скидки (от 0 до 100). Необязательное поле (по умолчанию 0).
* **Пример входа (JSON в теле запроса):**
```json
{
  "product_id": 1042,
  "store_id": 15,
  "period": "2026-11",
  "discount_percent": 10
}
```
* **Успешный код и пример ответа (Код 201 Created):**
```json
{
  "forecast_id": 501,
  "product_id": 1042,
  "store_id": 15,
  "period": "2026-11",
  "predicted_units": 1450,
  "confidence_interval": {
    "min": 1320,
    "max": 1580
  },
  "created_at": "2026-09-28T14:30:00Z"
}
```

### Операция 2: GET /forecasts/{forecast_id} (Чтение прогноза)
* **Обязательные поля и их смысл:**
  * `forecast_id` (integer, передается в пути URL) — уникальный номер ранее сохраненного прогноза.
* **Пример входа:**
  * Тело запроса не требуется. Запрос направляется по пути: `/forecasts/501`.
* **Успешный код и пример ответа (Код 200 OK):**
```json
{
  "forecast_id": 501,
  "product_id": 1042,
  "store_id": 15,
  "period": "2026-11",
  "predicted_units": 1450,
  "confidence_interval": {
    "min": 1320,
    "max": 1580
  },
  "created_at": "2026-09-28T14:30:00Z"
}
```

## 4. Ошибки и ограничения

| Операция | Ситуация | Код ответа | Пример ответа / понятное сообщение |
| :--- | :--- | :---: | :--- |
| `POST /forecasts` | Пропущено обязательное поле `period` или нарушен строковый формат даты | **400 Bad Request** | `{"error": "Validation Error", "message": "Field 'period' is required and must follow YYYY-MM format"}` |
| `POST /forecasts` | Передано недопустимое значение скидки (`discount_percent < 0` или `> 100`) | **422 Unprocessable Entity** | `{"error": "Unprocessable Entity", "message": "discount_percent must be an integer between 0 and 100"}` |
| `GET /forecasts/{forecast_id}` | Прогноз с запрошенным идентификатором отсутствует в базе данных | **404 Not Found** | `{"error": "Not Found", "message": "Forecast with id 999 does not exist"}` |

* **Формат периода, единицы измерения и допустимые значения:**
  * Поле `period` задается строго строкой в формате `YYYY-MM` (например, `"2026-11"`).
  * Поля `product_id` и `store_id` — строго положительные целые числа ($> 0$).
  * Прогнозируемый объем `predicted_units` измеряется в целых штуках товара и не может быть отрицательным числом ($\ge 0$).
  * Границы доверительного интервала `confidence_interval.min` и `confidence_interval.max` измеряются в штуках и удовлетворяют условию $\text{min} \le \text{predicted\_units} \le \text{max}$.
* **Правило совместимости для клиента:**
  * Существующие поля JSON-ответа (`forecast_id`, `product_id`, `store_id`, `period`, `predicted_units`), на которые завязана логика клиентских систем, запрещено удалять или переименовывать без изменения мажорной версии контракта (например, перехода на `/v2/`). Добавление новых необязательных полей в ответ допускается и не должно нарушать работу существующих клиентов.

## 5. Сверка с ПР № 1

* **Все ли операции имеют потребителя и назначение на контекстной схеме:**  
  Да, все спроектированные маршруты строго соотносятся со стрелками контекстной схемы ПР № 1: `POST /forecasts` и `GET /forecasts/{forecast_id}` реализуют взаимодействие с веб-кабинетом менеджера (Связь 3), `GET /forecasts` с query-параметрами обеспечивает пакетную синхронизацию с ERP/WMS (Связь 2), а `GET /metrics/accuracy` поставляет агрегированные метрики качества модели в BI-систему (Связь 4).
* **Какие связи относятся к интерфейсу другой системы, а не к вашему API:**  
  Поток чеков с кассовых узлов (Связь 1) и пакетная загрузка календарей и погоды через ETL (Связь 5) относятся к API сторонних систем-источников. Наш сервис выступает их клиентом, поэтому пути вроде `/pos/transactions` или `/weather/daily` в наш API-контракт не включаются.

## 6. Краткая защита

* **Почему главный ресурс называется именно так?**  
  Главный ресурс назван существительным во множественном числе — `/forecasts` («прогнозы»), что является базовым стандартом проектирования REST API. Клиент манипулирует сущностью через стандартные HTTP-глаголы: создание нового прогноза (`POST /forecasts`), запрос единичного ресурса (`GET /forecasts/{forecast_id}`) и получение коллекции по фильтрам (`GET /forecasts?store_id=...`).
* **Что получит клиент при неверном запросе?**  
  Клиент получит стандартизированный ответ протокола HTTP с кодом ошибки клиентской стороны (`4xx`) и телом в формате JSON, содержащим структурированное описание проблемы:
  * `400 Bad Request` — при синтаксических ошибках или пропуске обязательных полей (`period`, `product_id`).
  * `404 Not Found` — если запрошен несуществующий идентификатор прогноза.
  * `422 Unprocessable Entity` — если поля переданы, но нарушены бизнес-правила (например, отрицательная скидка).
